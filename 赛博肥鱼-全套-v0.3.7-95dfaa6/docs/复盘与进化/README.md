## 后续使用方式

1. 开始相关改进前，先读当日复盘及问题清单，确认已知限制和已完成工作。
2. 优先处理高频失败、信息缺失和执行能力缺口，再调整运营策略。
3. 每项改动对应一个问题编号，补充代码位置、测试结果和下一次实际运行结果。
4. 只有达到问题的验收条件才能标为已解决。离线通过、隔离回放通过和实际长局通过分别记录。
5. 保留原始失败及当日数据。后续结论写入新增日期的记录，并在问题清单中引用，避免覆盖历史。
6. 将规则提升为长期策略前，检查游戏版本、帝国路线、适用条件与反例，不将单局现象固化成普遍规律。

问题清单的状态：`open`（待处理）、`investigating`（待定位）、`blocked_by_capability`（能力缺口）、`fixed_in_daytime_validation`（日间已修复且有指定范围验证）、`measurement_gap`（观测缺口）、`partially_implemented`（部分实现）、`fixed_pending_live_validation`（代码及离线验证已完成，待实际会话验证）。未来可追加 `resolved` 和 `reopened`。

本目录属于本地项目文档，不会自动进入游戏模型的记忆或改变运行行为。后续需通过代码、提示和明确的验证流程落实改进。

`validated_in_isolated_live_session`表示指定范围已在独立存档实机验证，不表示全部命令、异常分支或整晚直播均已验收；范围和限制必须同时引用对应记录。
