# 直播接入与互动设计参考

核查日期：2026-10-26。本文说明 0.2.0 已实现的边界、真实接入步骤和设计来源。自动测试只使用本机模拟消息，不读取账号 Cookie、不调用付费 AI。

## 三条连接分别配置

| 连接 | 用途 | 当前实现 |
|---|---|---|
| 专用画面窗口 → 抖音直播伴侣 | 直播画面 | 9:16 小店采集窗口，只显示角色与场景；在伴侣添加「窗口」来源 |
| 小店音频 → BlackHole 2ch → 伴侣麦克风 | 配音与点歌曲目 | 应用自己的混音通道；本地监听单独开关，不修改 macOS 默认设备 |
| 弹幕来源 → 本机互动桥 → 导演 | 弹幕、礼物、关注、进场与点歌 | 带随机令牌的本机 HTTP / WebSocket 接收器，以及本机上游 WebSocket 适配 |

**窗口采集成功不等于弹幕已经接入。** 本机已在直播伴侣「场景四」添加标题为「赛博肥鱼 · 抖音直播采集（9:16）」的窗口，并以等比缩放铺满竖屏；预览已显示小店，麦克风为 BlackHole 2ch、输入 100%、系统声音采集 0%、仅输出不监听，没有点击「开始直播」。本版没有公开的直播伴侣弹幕导出接口可直接调用。因此，真实数据仍需一个由店长自己选择、在本机运行的转发来源。没有来源时可使用独立本地测试和互动排练，不显示成「已连接抖音」。

## 在应用里连接

1. 打开「直播连接」，点击「连接互动来源」。不使用已有上游工具时，将上游地址留空。
2. 查看实际显示的接入地址；默认端口为 `17831`。端口被其他程序占用时会选择空闲端口，保持对方程序不变，随后必须重新复制地址。
3. 用「复制连接信息」把本机端点与令牌交给自己的转发程序。令牌只用于本机输入认证，不是 DeepSeek、百炼或抖音登录密钥，不进入普通状态广播或导出日志。
4. 先点「接入自检」：它会实际通过本机 HTTP 验证认证和解析，但不会注入观众、触发 AI 或制造礼物收入。
5. 让来源发送一条真实弹幕，检查「收到」计数及运行日志，再测试点歌。暂停、静音与内容审核仍由小店导演统一处理。

重新启动应用会生成新令牌；「重置令牌」会让旧 HTTP 凭据和已连接的旧 WebSocket 失效。令牌仅提供给本机可信程序，不要粘贴到公开网站或聊天消息中。本机令牌认证不验证抖音平台签名，不能据此声称礼物已获平台核验，真实收入仍以平台账单为准。

## 标准 HTTP 发送方式

以下端口与令牌都是占位值，须替换为「直播连接」显示的实际值。发送到 `/events` 的消息会进入真实小店流程；真实 AI 模式下可能调用付费服务。只验证连接时把路径改为 `/test`。

```sh
curl --request POST 'http://127.0.0.1:17831/events' \
  --header 'Authorization: Bearer REPLACE_WITH_LOCAL_INPUT_TOKEN' \
  --header 'Content-Type: application/json' \
  --data '{"id":"room-a:message-001","kind":"chat","user":{"id":"stable-viewer-001","name":"晚睡的猫"},"text":"点歌 晚安"}'
```

标准事件的必要字段：

- `id`：平台稳定事件 ID。重连重发必须保持相同 ID，不能用当前时间随机生成替代，否则无法去重。
- `kind`：`chat`、`gift`、`enter`、`follow` 或 `like`。
- `user.id`：稳定用户 ID；不能用昵称代替。平台 64 位数字 ID 应以字符串发送。
- `user.name`：显示昵称，不用于判定身份。
- 弹幕提供 `text`；礼物提供 `giftId`、`giftName`、`count`。
- 连击的 `comboKey` 必须在同一次连击中固定，`count` 是累计数量。没有连击标识时，每个事件的数量只能代表该事件本身。
- `at`：毫秒时间戳，可省略并使用接收时间。

礼物连击可以先发送累计 2 个，再发送累计 5 个；第二条使用新的事件 ID 和相同的 `comboKey`，实际只增加 3 个。不要把服务端给出的累计数量自行再累加。

```json
{
  "id": "room-a:gift-snapshot-002",
  "kind": "gift",
  "user": { "id": "stable-viewer-001", "name": "晚睡的猫" },
  "giftId": "heart",
  "giftName": "小心心",
  "count": 5,
  "comboKey": "room-a:gift-group-001"
}
```

正常接收返回 HTTP `202`，JSON 中有 `ok` 和 `data.accepted`。格式错误为 `400/422`，认证错误为 `401`，错误来源 Host 为 `403`，错误媒体类型为 `415`，超大输入为 `413`。批次先整体解析和限流，再逐条交给导演；若业务层只接受了部分事件，应以 `accepted` 判断，并使用原事件 ID 安全重试。

## 标准 WebSocket 发送方式

使用「复制连接信息」中的 `websocketEndpoint`。浏览器 WebSocket 不能自定义 Authorization 请求头，所以这一端点把令牌放在查询参数；应用的状态与日志会排除这条完整地址。

```js
const socket = new WebSocket('ws://127.0.0.1:17831/events?token=REPLACE_WITH_LOCAL_INPUT_TOKEN')
socket.onopen = () => socket.send(JSON.stringify({
  id: 'room-a:message-002',
  kind: 'chat',
  user: { id: 'stable-viewer-002', name: '月亮邮差' },
  text: '今晚有什么故事？'
}))
socket.onmessage = event => console.log(JSON.parse(event.data))
```

这段代码只适合自己的本机转发工具。不要把令牌配置到公共托管页面。若第三方工具的 HTTPS 页面不能连接本机 `ws://`，请使用该工具支持的本机部署方式，不能以关闭浏览器安全保护来解决。

## 现有工具格式的兼容范围

### DouyinBarrageGrab 格式

本机上游地址示例为 `ws://127.0.0.1:8888`，格式选择「DouyinBarrageGrab」。兼容外层 `Type` 与 `Data`，其中 `Data` 可以是对象或 JSON 字符串：类型 1–5 分别映射弹幕、点赞、进场、关注、礼物；统计等消息忽略。64 位 ID 在 JSON 解析前保真。礼物连击结合 `GroupId`、`RepeatCount` 与 `Combo` 形成稳定累计快照。

[上游项目 README](https://github.com/ape-byte/DouyinBarrageGrab/blob/master/README.md)说明默认系统代理方案及可选 Windows 进程挂钩方式。本项目只兼容其输出协议，没有安装它、修改系统代理、安装抓包证书或注入直播伴侣。已有安全本机来源时可以对接；不把它作为这台 Mac 的默认采集组件。

### dycast 格式

[dycast README](https://github.com/skmcj/dycast/blob/main/README.md)公开了 `id / method / user / content / gift` 转发结构和 WebSocket 转发功能。如果店长自行运行它的本机实例，可将其转发目的地址设为小店的 `websocketEndpoint`；不需要填写小店的上游地址，因为这里是工具主动向小店推送。

本项目没有复制或打包 dycast 的签名、抓取或界面代码，只独立实现公开 JSON 的输入转换。弹幕、点赞、进场和明确的关注消息可解析；取消关注不会被算成关注。礼物的公开转发缺少可靠连击分组，当前保守地只接收明确 `repeatEnd = 1` 的最终快照；没有终结标记的礼物会跳过，不能声称完整计账。若要完整礼物数据，应由来源转换成带稳定 `comboKey` 的小店标准事件。礼物价格、角色权限及上游附带的个人资料不会透传进入小店。

这些协议适配已用离线样本验证，**尚未完成真实抖音直播间端到端验证**。第三方工具自身的登录、平台适配与稳定性不由本项目代管，不自动索取或读取其 Cookie。

## 不影响日常工作的边界

- 输入桥只监听 `127.0.0.1`，不会开放局域网或公网端口；上游也仅允许本机 `ws/wss` 地址。
- 不更改系统代理、浏览器证书、默认音频设备、其他项目配置或直播伴侣文件。
- 单包 64 KiB，整批最多 50 条事件；嵌套输入有深度和总量限制。
- 默认每秒补充 60 条额度、突发最多 120 条、待处理最多 200 条、最多 4 个入站 WebSocket 客户端。
- 主播关闭接收器后，旧连接与未投递批次失效；重连保留原平台事件 ID，由核心做去重与连击增量计算。
- 独立本地测试不会连接真实弹幕来源；真实配音和点歌仍从应用自己的直播总线输出，监听关闭只影响本机这条监听通道。

以上仅借鉴设计，没有复制这些项目的实现。点歌秩序是本项目独立实现：观众点歌只加入队列，每人最多一首待播并有冷却；可限制熟客或交店长审批；同名曲需明确歌手；普通「切歌」只算唯一用户的一票，保护时间及投票门槛同时满足才切换。店长保留直接操作权，观众不能通过附带 URL 或冒充管理员直接播放任意文件。
