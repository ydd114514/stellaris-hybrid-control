## 0. 一页总览

**要做的东西**：一个 macOS 应用（暂名「小店后台」）。它包含两个窗口：

1. **直播画面窗口**：1080×1920 竖屏，深夜小店场景里有一个 Q 版原创店主，会走动、做事、说话、做表情。抖音直播伴侣（Mac 版）用「程序窗口」采集这个窗口开播。
2. **后台窗口**：店长在这里一站式配置和操控：开始/暂停、看 AI 准备说什么并一键通过、点按钮让角色做动作、改人设、试听声音、设置礼物规则、看成本和日志。

**技术路线（已定）**

| 部分 | 选型 | 说明 |
|---|---|---|
| 应用外壳 | Electron + TypeScript + Vite + Vue 3 | 一种语言写完全部；Coopanion、AIRI 都用 Electron 并支持 Mac |
| 角色 | Q 版分层 2D + 程序动画，复用 Coopanion 的角色引擎（kit） | 自带 19 表情、18 动作、走跑坐睡、头发尾巴弹簧物理 |
| 对话 | DeepSeek API（可切换千问） | OpenAI 兼容接口 |
| 配音 | 千问 Qwen-Audio-TTS（云端 HTTP 流式） | 用"声音设计"生成原创店主声音 |
| 声音进直播 | 应用把配音直接输出到 BlackHole 虚拟声卡 | 直播伴侣把 BlackHole 选为声音输入 |
| 数据 | 本地 SQLite + JSON 配置；密钥存 macOS 钥匙串 | |
| 弹幕礼物 | 可插拔的"输入源"，先用模拟器 | 抖音来源受合规限制，见第 2、8 节 |

**不再作为运行依赖的东西**：NachoBot（Python、Windows 启动脚本、QQ 耦合、无 Mac 渲染端）只借鉴它的设计（优先队列、礼物合并、冷场发言、直播快速回复路径、观众画像），不打包进应用。

**最大的前提风险**：抖音平台规范要求虚拟人直播"由真人驱动进行实时互动"，不允许完全由 AI 驱动互动（见第 2 节）。因此本应用默认是"真人驱动 + AI 辅助"，全自动模式只用于本地测试。开播前必须先完成合规确认（第 11 节 C 线）。

## 2. 必须先知道的平台与法规事实

1. **抖音《关于人工智能生成内容的平台规范暨行业倡议》（2023-05-09 发布，已核实媒体对原文的引述）**：直播使用虚拟人须在平台注册形象，运营者须实名认证；须由真人驱动进行实时互动；不允许完全由人工智能驱动进行互动。没有查到废止记录，按仍有效处理。
2. **《人工智能生成合成内容标识办法》（2025-09-01 施行）**：显式标识指以文字、声音、图形等方式添加、用户能明显感知的标识；任何组织和个人不得删除、篡改、隐匿标识。
3. **《数字虚拟人信息服务管理办法（征求意见稿）》（网信办 2026-04-03 发布，据律所解读）**：展示区域全程标注含"数字人"字样的显著标识；严禁向未成年人提供虚拟伴侣等虚拟亲密关系服务；禁止诱导沉迷和过度消费；建立防沉迷机制。正式版以官方为准。
4. **直播伴侣 Mac 版（官方公告，已核实）**：支持 macOS 13 以上的 Intel 和 Apple 芯片 Mac；可采集摄像头、桌面、程序窗口、图片并开播；更多功能陆续开发。官方没有说明能否采集电脑内部声音，所以用 BlackHole。
5. **官方互动数据通道（旧文档已核实）**：直播小玩法要求真人出镜、禁止挂机，且禁止借小玩法获取互动数据另作他用；互动工具暂停新插件准入。

**对设计的直接影响**

- 默认运行模式是"真人驱动"：AI 起草，店长确认或接管（第 3.3 节）。
- 直播画面常驻"AI 数字人"标识，不可关闭。
- 陪聊内容不做"虚拟恋人"人设；礼物玩法不得诱导过度消费（第 9、10 节）。
- 抖音弹幕礼物来源要单独做合规判断（第 8 节）。

## 3. 产品形态

### 3.1 直播画面（竖屏 1080×1920）

从上到下的分区（具体比例在 M1 用抖音 App 实际截图校准，避开抖音原生的顶部信息栏、右侧按钮列和底部评论区）：

- **顶部窄条**：小店名、"AI 数字人"标识、今晚营业目标进度（可选）。
- **中部主舞台**：小店场景（后墙、窗、货架、柜台、前景道具分层），店主在其中走动。占画面主体。
- **对话气泡**：跟随角色头顶；同时在固定位置显示字幕，字随语音逐字推进。
- **右侧或底部小面板**（可在后台开关）：熟客榜/"股东名单"、礼物反应提示、点单/投票结果。
- **环境小动画**：窗外下雨、台灯微闪、杯子冒热气、招牌灯。

### 3.2 后台（店长控制台）

| 页面 | 功能 |
|---|---|
| **导播台**（首页） | 直播画面实时预览；状态灯（对话模型、配音、输入源、BlackHole、预算）；开始营业 / 暂停 / 紧急静音 / 打断当前发言；当前队列 |
| **真人驱动台** | AI 起草的下一句话和动作，按钮：通过（快捷键）/ 修改后发送 / 跳过；输入框直接让店主说一句；动作和表情按钮墙（像音效板一样点一下就做）；点位按钮（去柜台、去窗边） |
| **角色** | 人设表单（名字、性格、口头禅、禁区话题、说话长度）；声音：选音色、用文字描述生成新音色、语速/语气指令、试听；外观：服装和配色切换 |
| **动作库** | 所有动作的列表、预览按钮、启用开关、给 AI 看的动作说明、所属点位 |
| **礼物规则** | 表格：礼物 → 反应动作 + 台词模板 + 小店永久变化；每行有"测试"按钮 |
| **小店** | 已解锁的装修和道具、今晚故事状态、营业目标设置、重置 |
| **观众** | 熟客列表、备注、屏蔽名单 |
| **安全** | 违禁词表、过滤强度、哪些内容必须人工确认 |
| **成本** | 今日/本场 token 和字符用量、折算金额、预算上限和超限后的降级策略 |
| **日志** | 完整对话记录、错误、每次回复的耗时分解，可导出 |
| **设置** | API 密钥（存钥匙串）、音频输出设备、画面分辨率、安全区辅助线开关 |
| **模拟器** | 手动注入弹幕、礼物、连击、进场，测试一切流程 |
| **首次设置向导** | 逐项检查：密钥能否调通、BlackHole 是否存在、试听声音、直播伴侣采集说明 |

设计原则：店长不需要碰任何配置文件或命令行；所有设置都有表单、默认值和"测试"按钮；出错时用中文说明原因和下一步。

### 3.3 运行模式

| 模式 | 行为 | 用途 |
|---|---|---|
| 真人驱动（默认） | AI 起草回复和动作，店长通过后才说；店长可随时直接输入台词或点动作 | 开播默认 |
| 真人监督 | AI 直接说，店长可随时打断、改写、接管 | 是否满足平台"真人驱动"要求待确认，确认前不在抖音使用 |
| 全自动 | 完全由 AI 运行 | 仅本地测试和录样片 |

无论哪种模式，礼物反应、冷场小动作、日常循环这类不涉及对话的表演都可以自动进行。

## 4. 系统架构

```text
┌──────────────── 小店后台（Electron 应用）────────────────┐
│                                                          │
│  后台窗口（Vue）          直播画面窗口（舞台页）          │
│   导播台/真人驱动台  ⇄    场景 + 角色引擎 + 气泡字幕     │
│   配置/模拟器/日志        音频播放 → BlackHole            │
│          │                       ▲                       │
│          ▼                       │ 舞台指令/完成回执      │
│  ┌──────────── 主进程服务（Node/TypeScript）──────────┐  │
│  │ 输入源 ─► 事件总线 ─► 导演（调度/队列/日常循环）    │  │
│  │                         │            │              │  │
│  │                    大脑（对话）   配音（千问 TTS）   │  │
│  │                    记忆 SQLite    安全过滤  成本统计 │  │
│  └─────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
        ▲ 弹幕/礼物                     │ 画面 + 声音
  模拟器 / 抖音来源                 直播伴侣（Mac）→ 抖音
```

**模块清单**

| 模块 | 职责 |
|---|---|
| `inputs` | 输入源接口：模拟器、后台手动输入、抖音来源（第 8 节）。统一转成标准事件 |
| `bus` | 事件总线：弹幕、礼物、进场、关注、后台指令、舞台回执 |
| `director` | 导演：选择回应哪条弹幕、排队、优先级、动作衔接、礼物表演、冷场和日常循环 |
| `brain` | 组装提示词，调用对话模型，解析结构化回复 |
| `memory` | 观众画像、熟客、小店状态、故事进度、对话摘要（SQLite） |
| `voice` | 千问流式合成、音色管理、逐字时间戳 |
| `stage` | 舞台页：场景、角色引擎、气泡字幕、音频播放和嘴型 |
| `safety` | 输入过滤（注入、违禁词）、输出审核、人工确认规则 |
| `cost` | 从每次 API 返回的用量实时计费，预算上限和降级 |
| `console` | 后台界面 |
| `config` | 配置读写、密钥（Electron safeStorage / 钥匙串） |

**一次互动的数据流**

1. 输入源产生"观众 A：这么晚还不关门？"。
2. `safety` 过滤输入；`director` 决定现在回应它（不在说话、优先级够）。
3. `brain` 带上人设、熟客记忆、小店当前状态、可用动作清单，请求对话模型，得到结构化回复。
4. `safety` 审核输出；真人驱动模式下送到后台等待店长通过。
5. 通过后，`voice` 开始流式合成；舞台先切表情、开始动作，第一段音频到达即开始播放，嘴型和字幕跟随。
6. 舞台回报"语音播完""动作完成"，导演再安排下一件事；`memory` 记下这次互动。

**为什么不用 NachoBot 当后端**：它的价值（人格、记忆、直播队列）可以用几个 TypeScript 小模块实现；而它的代价是 Python 运行时、Windows 启动脚本、QQ 平台耦合、原生 Live2D 渲染端在 Mac 不可用，以及 GPL 许可。一个语言、一个安装包，对"好配置"最有利。

## 5. 角色系统（核心）

### 5.1 复用 Coopanion 角色引擎（已核实源码）

来源：Coopanion 仓库 `packages/cortico-world-desktop-pet/web/`，许可 AGPL-3.0-or-later（`web/whale/` 鲸鱼娘贴图除外，不得用于本项目直播和发布）。

已有能力：
- `kit/rig.js`：小型类 Live2D 渲染器，每个部件是一张贴图铺在网格上，网格逐帧经过变形器链（绕枢轴转动、缩放平移、矩形位移场），WebGL2 绘制，WebGL1 兜底。
- `kit/body.js`：身体逻辑。表情 19 个：neutral、happy、wink、love、shy、surprised、angry、sad、sleepy、thinking、smug、pout、worried、determined、flustered、scared、excited、cry、confused。动作 18 个：stand、jump、hop、look、turn、nod、shake、spin、sit、sleep、dizzy、walk、run、wave、bow、shiver、flap、dance。另有走到指定位置、坐下、打盹、倾听、思考、说话嘴型。
- 身体接口：`step(dt)`、`layout()`、`do(word)`、`walk(x, run, id)`、`move(...)`、`place(x, facing)`、`set(state)`、`talk()`、`setScheme(id)`；事件：`arrived`、`interrupted`、`done`（一个词做完）、`mode`。`done` 即动作完成回执。
- 形象包：`figure.json`（含 `vocab` 词表：每个词的名字、给 AI 看的说明、时长）+ 工厂脚本 + 贴图。包可以注册自己的表情和动作；自定义动作按每帧给出的 `frame.gesture = { kind, k: 0..1 }` 自己画。
- 示例页 `examples/whale/` 可脱离桌宠应用、在普通浏览器页里运行，证明引擎可以嵌入我们的舞台页。
- 项目有 macOS 打包配置和 Mac 实测记录。

需要改的地方：
- `talk()` 目前只是把说话强度置 1 后衰减（为音节音效设计）。改为接收每帧音量（0–1），由真实语音驱动。
- 桌宠专属行为（被鼠标拎起、甩出、站在其他窗口边缘）在舞台上关闭。
- 地面不只一条线：舞台定义"点位"（柜台后、货架前、窗边、门口），角色在点位之间走。柜台等前景层要能挡住角色下半身（舞台按图层顺序合成）。
- 许可：使用并修改 AGPL 代码，建议整个应用以 AGPL 开源（见决策 D1），角色美术、声音、人设文本另行保留权利（Coopanion 自己也是这样处理美术的）。

可借鉴（MIT，可直接复用代码）：AIRI 的表情过渡、眨眼、视线、元音口型（`model-driver-lipsync`，基于 wLipSync）。

**角色固定侧身朝右，转身时整体镜像**：衣服上不放文字和不对称标志；所有动作按侧身设计；"面向镜头"类动作用转头、视线和手势表现。

### 5.2 动作清单

每个动作在清单里的字段：

```jsonc
{
  "id": "wipe_cup",
  "names": ["擦杯子"],
  "about": "拿布慢慢擦玻璃杯，偶尔对着灯看一眼",
  "kind": "motion",
  "body": "upper",          // upper 上半身 / full 全身
  "station": "counter",     // 需要在哪个点位，null 表示任意
  "props": ["cup", "cloth"],
  "seconds": 4.0,
  "loopable": true,         // 可作为待机循环
  "interruptible": true,
  "while_talking": true,    // 说话时能否做
  "gift_only": false
}
```

**首批动作（M5 交付）**：

| 类别 | 动作 |
|---|---|
| 柜台 | 擦杯子、冲咖啡/倒饮料、把杯子推向镜头方向、趴柜台、托腮听、写便签、算账拨算盘 |
| 店内 | 整理货架、浇窗台的花、看窗外下雨、开关招牌灯、扫地 |
| 情绪类 | 伸懒腰打哈欠、偷笑捂嘴、叉腰、比心、举杯致谢 |
| 礼物专属 | 每种小礼物一个明确表演（示例见第 9 节） |

扩充原则：先把 20 个高频动作打磨到不僵硬，再按直播数据（哪些动作被触发得多、观众反应好）逐批增加。每个新动作 = 少量补画（手臂姿势、道具）+ 一段动作函数 + 清单条目 + 预览测试。

### 5.3 导演规则

- 一个时刻只有一个"主动作"；表情、视线、嘴型独立叠加。
- 说话时只做 `while_talking` 为真的动作；全身动作和走路在两句话之间进行。
- 需要点位的动作：先走过去（`walk` → `arrived`），再做。
- 礼物反应优先级最高，但等当前这句话说完；连击合并成一次加强版表演，不排长队。
- 同一动作不连续出现；最近 N 个动作降低权重。
- 每个动作都要等 `done` 或超时（时长 × 2）后才进入下一个，超时记日志。
- AI 给出清单外的动作名：丢弃并记日志，不报错、不卡住。
- 暂停/紧急静音：立即停止音频、清空队列、回到待机。

### 5.4 小店日常循环

没有互动时，导演按"日常剧本"自动安排，避免角色僵站：
- 一个按时段加权的活动表（深夜前段多做饮料和整理，后段多发呆、看雨、打哈欠）。
- 每隔 20–60 秒（可配置）换一件事；偶尔自言自语一句（预设台词池 + 少量 AI 生成，生成内容也走安全审核）。
- 和小店状态联动：新解锁的装饰会出现"看一眼、摸一下"的小动作。

### 5.5 嘴型、字幕、气泡

- 嘴型：舞台用 Web Audio 播放千问返回的 PCM，每帧取音量驱动张嘴幅度；进阶版接 wLipSync 输出元音权重（需要一份校准配置，按其文档在 uLipSync 里制作），对应 Q 版嘴型贴图（a/i/u/e/o 和闭嘴）。
- 字幕：千问流式合成可返回逐字时间戳（`word_timestamp_enabled`），按播放进度逐字显示。
- 气泡：一句话分成短段显示，长句自动换行，停留时间跟语音对齐。

### 5.6 美术生产流程（需要店长参与审美确认）

参考 Coopanion 鲸鱼娘的已公开流程（全部贴图由 AI 图像模型生成和编辑）：

1. **设定**：店长确认外形关键词（发型、配色、围裙、小店元素）。AI 生成 3–5 张候选设定图，店长选一。
2. **母版立绘**：侧身三分之四朝右、二头身、平涂、干净线稿、纯色背景。
3. **拆件**：对母版做一系列"去掉某部分并补画下面"的编辑（去头、去手臂、去尾巴/饰物、去裙子露腿、去前发、抹掉五官……）；每张编辑图配准回母版坐标，和上一步相减得到部件遮罩；可见区域用母版原像素，被挡区域用补画像素。
4. **五官和表情**：眼睛拆成睫毛、眼白、虹膜；开心、睡着、惊讶、喜欢、晕等用整张替换贴图；其余用程序绘制叠加。
5. **坐姿下半身**、**动作专用手臂和道具**：同样用编辑方式生成。
6. **人工修图**：检查描线断口、颜色不一致、边缘残留。
7. **打包**为形象包，跑全部表情和动作的截图测试。

工具：
- 图像生成和编辑：千问百炼的图像模型（如 `qwen-image-3.0-pro`，支持编辑，可程序化调用，以模型广场为准）；店长的 ChatGPT 会员可用于手工出图（是否有 API 权限未核实）。
- 辅助拆层（可选，需云 GPU）：See-through（SIGGRAPH 2026，代码 Apache-2.0，单张动漫图拆成约 23 层 PSD，需 8–16GB 显存的 NVIDIA/AMD 显卡，权重许可未说明，实测主要是正面站姿）；Qwen-Image-Layered（Apache-2.0，可变层数 RGBA 分解，需 CUDA）。二者只作为初稿，最终以第 3 步的编辑流程为准。
- 场景：同样 AI 生成后分层（后墙、窗、货架、柜台、前景），保持和角色一致的线稿和配色风格。

## 6. 大脑（对话）

### 6.1 结构化回复

要求模型只输出 JSON（使用 JSON 模式或函数调用，解析失败自动修复一次，再失败则丢弃）：

```json
{
  "reply_to": "viewer_123",
  "say": ["你都还没睡，", "我关门了谁收留你这位精神股东。"],
  "face": "smug",
  "action": "wipe_cup",
  "station": null,
  "voice_style": "慵懒，带点调侃",
  "memory_note": "viewer_123 经常深夜来"
}
```

- `face` 和 `action` 只能取当前词表中的词（提示词里附上动作说明）。
- `say` 分句，便于边合成边播放。
- `voice_style` 映射到千问的语气指令（可选）。

### 6.2 提示词组成

人设（后台表单生成）→ 平台和安全规则 → 小店当前状态和今晚故事 → 这位观众的熟客记忆 → 最近几轮对话摘要 → 可用表情和动作清单 → 当前弹幕。人设和规则放在固定前缀，利用对话模型的缓存降低成本。

### 6.3 选哪条弹幕回应

借鉴 NachoBot 直播模式：
- 优先级：礼物 > 熟客点名 > 提问 > 普通聊天 > 进场；同类按新鲜度。
- 每 N 秒最多回应一条，其他弹幕合并为"现场氛围"摘要。
- 重复刷屏、广告、明显的提示词注入直接忽略。
- 冷场超过阈值触发日常循环或自言自语。

### 6.4 记忆

SQLite 表：`viewers`（平台 ID、昵称历史、来访次数、偏好、备注、是否屏蔽）、`shop_state`（装修、道具、营业额、故事进度）、`events`（全部输入事件，含去重键）、`utterances`（说过的话）、`summaries`（每场摘要）。观众身份以平台稳定 ID 为准，不以昵称为准。

### 6.5 对话模型

- 默认 DeepSeek（OpenAI 兼容接口），可在后台切换为千问或其他兼容接口。
- 直播回复走快速路径：不开深度思考，限制输出长度，目标是选中弹幕到开口的总延迟 ≤ 3 秒（M3 实测后定）。
- 价格不写死：在后台填单价，按每次返回的用量计费。

## 7. 声音

- **接口**：千问 Qwen-Audio-TTS HTTP 接口，请求头 `X-DashScope-SSE: enable` 开启流式，`format: "pcm"`，`sample_rate: 24000`；流式事件里 `output.audio.data` 是 base64 音频块，`finish_reason: "stop"` 结束。地址需带业务空间 ID：`https://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/services/audio/tts/SpeechSynthesizer`；北京和新加坡地域的 Key 不通用。
- **模型**：`qwen-audio-3.1-tts-flash` 起步（北京地域标价：输入每百万 token 0.212 美元、输出 1.696 美元，每分钟 180 次请求上限）；音质不够再试 `plus`。
- **原创音色**：用"声音设计"接口（`/api/v1/services/audio/tts/customization`，`model: "voice-enrollment"`，`action: "create_voice"`），用不超过 500 字的文字描述生成音色并返回试听；创建免费，按目标模型的合成量计费；生成的音色只能配合创建时指定的模型使用。后台"角色 → 声音"页把这一步做成表单 + 试听按钮。
- **语气**：每句可带 `instruction`（如"压低声音，偷偷说"），由回复里的 `voice_style` 映射。
- **逐字时间戳**：`word_timestamp_enabled`（仅流式）用于字幕。
- **播放和路由**：舞台页用 Web Audio 播放；通过 `setSinkId` 把输出设到 BlackHole 2ch；后台可选择同时在 Mac 扬声器监听（需实测 Electron 中的行为）。
- **兜底**：配音失败或超时，舞台只显示气泡文字并做"思考/抱歉"表情；连续失败自动切到纯文字模式并在导播台亮红灯。

去重按事件 ID；礼物连击按 `comboKey` 只处理增量；断线重连后不重放已处理事件。

## 9. 玩法设计（好点子）

来自参考直播间、成功案例和本项目设定：

1. **透明账本**：参考截图的 token 消耗/余额/盈亏面板，包装成"小店电费账单"：今晚 AI 花了多少、观众礼物撑起了多少，形成"大家一起养这家店"的感觉。
2. **营业目标**：借鉴 AI 主播"紫樱"的挑战结构（2 小时营业目标，48 小时累计营收约 4.2 万元、峰值在线 4 万），改成温和版：今晚达成营业目标就解锁一件新装修或新饮品，不做"失败清零"这种强刺激，避免诱导过度消费。
3. **熟客制度**：记住常来的观众、他们常点的饮品和说过的事，再来时主动招呼；熟客榜显示为"小店股东名单"。
4. **共同养成的永久变化**：礼物和投票带来的装修、道具、植物长大，下一场还在。
5. **观众命名和投票**：给店里的猫、新饮品、今晚的小故事走向投票。
6. **礼物 → 明确表演**（示例）：小心心 → 比心并冒爱心；棒棒糖 → 店主含着糖说话；咖啡类礼物 → 现场冲一杯推给镜头；较大礼物 → 换装或点亮新招牌。每个礼物的表演 3–6 秒、一眼看懂。
7. **时间感**：真实时钟驱动的打烊仪式、凌晨的困倦状态、雨夜特别台词。
8. **大方承认是 AI**：人设里允许拿"我是 AI"开玩笑，既合规又有梗。
9. **点歌**：参考直播间有点歌和歌词，但涉及音乐版权和抖音音乐规则，放到最后评估；先用"店里的唱片机"播放可商用的 BGM。

避免：动作机械重复、回应和上下文无关（紫樱案例总结的主要沉浸感杀手），这正是第 5 节导演规则和日常循环要解决的。

## 10. 安全、合规与成本

- **输入**：违禁词表；识别"忽略之前的指令"一类注入，按普通聊天处理且不执行；观众文本在提示词里明确标为"观众说的话"，不作为指令。
- **输出**：违禁词表 + 可选的百炼 AI 安全护栏（请求头 `X-DashScope-DataInspection`，需先开通，按 token 计费，单次不足 1000 token 按 1000 计；只对百炼上的模型调用生效，若要覆盖 DeepSeek 需经百炼调用 DeepSeek，需确认）。
- **人工确认**：真人驱动模式下全部台词需确认；任何模式下，涉及金钱、个人信息、医疗法律、未成年人话题的回复强制人工确认。
- **标识**：舞台常驻"AI 数字人"标识，后台无法关闭。
- **未成年人与消费**：不做虚拟恋人人设；不出现"刷礼物才理你"之类话术；礼物玩法有每人每场上限提示。
- **成本**：按 API 返回的用量实时累计；后台设每场和每日预算；达到 80% 提醒，达到 100% 自动降级（只做动作和预设台词，停止生成和配音）。

## 12. AI 自主开发规范

- **仓库结构**（pnpm workspace）：
  `apps/desktop`（Electron 主进程和后台界面）、`apps/stage`（舞台页）、`packages/director`、`packages/brain`、`packages/voice`、`packages/inputs`、`packages/memory`、`packages/safety`、`packages/shared`（事件和类型）、`vendor/coopanion-kit`（引入的引擎代码，保留原许可和出处，修改处加注释）、`assets/figure`、`assets/scene`。
- **固定版本**：锁定 Electron、Node、依赖版本；引入的开源代码记录仓库地址和提交号。
- **模拟优先**：对话、配音、输入源都有模拟实现，所有自动测试不花钱、不联网；真实 API 只在标明的手动测试里调用。
- **可视化验证**：舞台的每个动作和表情都有 Playwright 截图测试；动作关键帧（k = 0、0.5、1）各截一张存档，便于人工复查和回归对比。
- **完成定义**：类型检查和测试通过；新增功能在后台有对应入口或开关；中文错误提示；日志里能看到它在做什么；更新本文对应章节的状态。
- **不确定时**：涉及审美（美术、声音、人设措辞）、花钱、合规的决定，停下来在后台或对话里问店长；技术细节自行决定并记录理由。
- **安全**：密钥只存钥匙串；日志中不打印密钥和完整观众个人信息。

| D3 | 开播时用哪种运行模式 | 真人驱动；"真人监督"在抖音明确认可后再用 |
| D4 | 对话模型 | DeepSeek 默认，千问作备选，后台可切换 |
| D5 | 美术出图工具 | 百炼图像模型（可程序化，便于 AI 自动拆件）；ChatGPT 手工补充 |
| D6 | 是否做点歌 | 暂不做，先用可商用 BGM |

## 15. 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 抖音不认可 AI 辅助的运行方式 | 无法在抖音开播 | 线 C 提前确认；产品默认真人驱动 |
| 非官方弹幕来源被封或失效 | 互动中断、账号风险 | 不作为默认；插件隔离；随时可切回手动 |
| AI 拆件不一致（描线、颜色） | 角色看起来廉价 | 母版配准流程 + 人工修图 + 截图验收 |
| 手拿道具的动作成本高 | 动作扩充变慢 | 先做 20 个高频动作；按数据决定后续 |
| 云端配音延迟或网络抖动 | 冷场、口型不同步 | 流式播放；超时兜底；导播台显示延迟 |
| 成本失控 | 亏钱 | 实时账本、预算上限、自动降级 |
| AGPL 合规 | 法律风险 | 决策 D1；保留许可和出处；公开源码 |
| 直播伴侣 Mac 版功能变化 | 采集方式失效 | 每次更新后跑一次采集检查；保留 OBS 推流作为备选（需另行确认推流权限） |
